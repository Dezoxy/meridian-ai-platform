### S021 — Identity
**Status:** doing · **Started:** 2026-10-07 · **Finished:** — · designed in
plan PLAN-VERSION; the code of the token check, the cookie and the guard is
built and tested since 2026-10-08 and wired to no route (the part of that date,

**Goal:** staff sign in, on kind through a mock issuer and on Azure through
Entra ID, and the Claims API checks who is calling, in which role and for
which tenant, before any claim is read or decided. This record is the design
and the threat rows, written before the first line of code, from the owner's
answers of 2026-10-07; the sentences down to "Work log" are that design as
it was written (only the threat ids follow the register). **As of 2026-10-07
nothing of sign-in was built;** the part of 2026-10-08 says what is built
since. It is modules and tests that no route calls: no issuer runs on kind, no
route checks a token, no cookie is set, and every route of the Claims API is as
open as it was (hard rule 7: everything below that the 2026-10-08 part does
not list as built is designed).

**Two halves.** The kind half needs nothing from Azure: a Keycloak on the local
cluster, the app's own checks, the staff roles, the tenant from the token and
the actor on the decision row. It depends on nothing unbuilt. The Entra half
replaces the mock issuer with Entra ID (app registrations, the roles as app
roles, the issuer and audience pinned per environment, the mock refused outside
kind) and waits for S020's apply. The tenant question (Part D, 5) is answered:
stay in the trial's tenant.

**The cut into three steps, and why.** The advisor's reading (below) cut the
step before work began. S021 keeps the staff half. **S093** (claimants sign in
as themselves) takes the second population: their realm, their session, a
claim owned by the claimant who filed it, and its migration. **S094** (sign-in
at the edge) takes the second layer: TLS at kind's edge and Envoy Gateway's
rules. The reasons: the first draft was eight contracts and two migrations
for one step; the claimants' half adds a realm, a session, a migration and a
product rule (what a claimant may see) that the staff half does not need; and
the edge half has facts of its own (the proxy forces `Secure` cookies, two
namespaces need new egress, six paths only a run can show) and needs TLS at
the edge, which nothing else does. S022 and S026 still depend on S021 alone;
whether either also waits for S093 or S094 is open (below).

**The facts that decide the shape** (the session's maps and facts sheet, read
on 2026-10-07, nothing run): the edge on kind is plain HTTP, and Envoy's
sign-in forces `Secure` cookies; the model and the threat model already say the
app validates tokens (TB-2, T-05); PyJWT with crypto is locked, through another
package, and no session library is; Entra's `roles` claim is a list in both
tokens and a person is keyed on `tid` and `oid`; no mock issuer fits without a
trade (Dex: static users, `groups` only, no logout; mock-oauth2-server: any
claim, no passwords; Keycloak: everything, at least 750 MB).

**Decisions** (D1 to D10, as the design has them after the advisor's reading;
the owner may overturn any that the answers above do not state):
- **D1, one Keycloak, two realms.** `meridian-staff` (four roles, delivered as
  a `roles` list claim in the access and the ID token) and `meridian-claimants`
  (S093). Two realms are two issuers, as Entra ID and Entra External ID are, so
  one instance is honest for two populations. A namespace `identity` of its
  own, default-deny; the image pinned by digest with a Renovate reader;
  development mode with its built-in database, so nothing persists and a
  restart makes new keys; the realm files generated at `make up`, with the
  test users' passwords and the clients' secrets made by `openssl rand` into a
  Kubernetes Secret, never committed (T-06). The memory is Keycloak's own
  floor, 750 MB, and the room is measured, not assumed (Y2's stop, below).
- **D2, one issuer name for the browser and the pods.** The browser reaches
  Keycloak through the edge on a second `.localhost` host name; pods reach it
  by its Service. Keycloak's hostname options are meant to keep `iss` the front
  name while the back channel answers on the Service name; the documentation
  does not say what `iss` is on a back-channel call, and a run will. The app
  pins the issuer string per environment and takes the key and token URLs as
  settings. Y2 changes a pinned fact on purpose: the edge admits routes from
  `meridian` only, and Keycloak's route lives in `identity`.
- **D3, the app layer, in a platform module** (`platform/common`, no agent
  framework, no provider SDK). A bearer check for the JSON routes: PyJWT a
  direct dependency, RS256 only, the key set fetched with a bounded cache and
  a timeout, one refetch at most per interval for an unknown key id, issuer,
  audience, expiry, not-before and subject required, a role required per
  route. For the pages, the authorization-code flow with PKCE run by the app,
  `state` and `nonce` checked; after the ID token is validated, a session
  cookie the app signs (HMAC, a key from a Secret) that holds the realm, the
  subject, the roles and the expiry and no token; no server-side store and no
  refresh, so the session ends with the token's life; `HttpOnly`,
  `SameSite=Lax`, and `Secure` everywhere but kind, and the app refuses to
  start without `Secure`, or with the mock issuer, outside kind (T-06); a
  logout that clears the cookie and goes to Keycloak's end-session. **As
  amended by the advisor:** the app enforces the cookie's own expiry on every
  request; the cookie lives no longer than Keycloak's session; a stolen cookie
  cannot be revoked before it ends, which is stated for both populations and
  is a threat row (T-116); the rate store's Redis exists if a store is ever
  wanted. **And a switch:** `MERIDIAN_SIGNIN`, off by default, the repository's
  own pattern, so the contracts land in pieces while kind keeps working; it
  flips when the scripts have their tokens (D7). While it is off every route
  is as open as today (T-119).
- **D4, two populations in the Claims API.** Staff routes (`/adjuster/*`, the
  decision, triage and brief routes): a staff session or token with the
  adjuster role. That is S021. The claimant routes (`/claimant/*`), ownership
  of a claim by the subject that filed it, the refusal of another claimant's
  status, documents, withdrawal and uploads with the answer an unknown claim
  gets, and a claim without an owner being staff-only: that is **S093**, with
  its migration.
- **D5, who decided, narrowed.** The decision row carries the actor now: the
  issuer's realm and subject (pseudonymous; no name or e-mail in a row, a log
  or a span), by a migration; that is T-32's promise. The audit rows get their
  actor in S085's outbox shape, because ADR 10 gives the audit model's next
  change to S085. One migration fewer in this step. The audit table's shape is
  read with the database reviewer first.
- **D6, the tenant from the token.** The registry (`tenants.yaml`) gains who
  may act for a tenant: a realm and a role or group. The Claims API resolves
  the tenant from the validated token through it, and the setting stays as the
  service's own bound. The registry's schema changes, so its README's "Change
  it" rules apply: the schema first, then `meridian registry validate`.
- **D7, scripts.** `make demo`, smoke's page checks and `meridian eval run`
  get a token from Keycloak without a browser (a confidential client with
  client credentials; its secret from the Secret, never printed). The switch
  flips when they have it.
- **D8, service to service stays as it is** (mutual TLS, ADR 4). The person's
  identity stays inside the Claims API's rows; what the runtime and the tools
  learn of it is the services split's question (S084, S085).
- **D9, the edge layer is S094,** a step with a row, not a "later".
- **D10, fingerprints and lanes.** No evaluation fingerprint may move (to be
  shown by the replay, not assumed). The migration waits for the uploads'
  migration to be on `main` (numbers are taken late; one migration lane).
  Keycloak on the cluster waits for the cluster lane.

**Two reviews of the module (Y1), 2026-10-07, and what they changed.** A
platform-boundary review (no critical, no high, three medium) and a security
review (no critical, two high, eight medium); both say approve with fixes,
and the security review found no forged token, no algorithm confusion and no
forged cookie in its probes. Nothing uses the module, so none of this was
reachable. The fixes are contract Y1b, and no route is wired (Y4) before it
is in. The design changes in five places:
- **An unreachable key URL answers 503, not 401,** when no usable key is
  cached; a key id nobody has stays 401. A 401 makes a client drop its
  session and sign in again in a loop, and hides an outage from a dashboard.
- **`nbf` is checked when present and no longer required;** `exp`, `iss`,
  `aud` and `sub` are required, and an `iat` further ahead than the leeway is
  refused. Requiring `nbf` gave no security (the signature covers the
  claims) and would refuse an issuer that does not send it.
- **The key fetch** (both high findings): the response is asked for
  uncompressed and a compressed one is a failed fetch (a 199 KB compressed
  answer peaked at 437 MB in the review's probe); a cached key is served
  without waiting for a fetch in flight, a fetch has a total deadline, and a
  failed fetch and a stale key each log a warning.
- **A token's kind and who it was issued to** can be required by two settings
  that are empty until Y2 has decoded a live token; without them an ID token
  with the right issuer and audience passed as an access token.
- **The principal says how it was authenticated** (bearer or cookie) and
  which issuer it came from, so a route that changes state can demand a
  same-origin check on the cookie path and later rows key a person by issuer
  and subject. The session's cap is also enforced when a cookie is opened,
  the key URL is HTTPS outside kind, and the session key is base64 of at
  least 32 bytes.

**Built, contract by contract.**
- **Y1, the module** (four files in `src/meridian/platform/common/`, 488, 468,
  355 and 374 lines): `signin.py` holds `check_bearer` (a token in, a
  `Principal` or a refusal out), the settings and the refusal classes;
  `signinkeys.py` holds `KeySet`, the issuer's key set with a bounded cache;
  `signinsession.py` seals and opens the cookie; `signinguard.py` holds the
  FastAPI dependencies and the walk of an app's routes. `pyjwt[crypto]` is
  pinned as a direct dependency. It refuses a token that is not RS256 before it
  looks at a key (`none`, an HMAC made from the public key, ES256, PS256,
  RS384, RS512, a header with no `alg`), another issuer, another audience, a
  missing expiry or subject, a time outside 30 seconds' leeway and a token over
  8,192 characters; a cookie is `v1.<payload>.<mac>`, an HMAC-SHA-256 compared
  in constant time, that holds the population, the issuer, the subject, the
  roles and the expiry and no token. After Y1 the tests under
  `tests/meridian/common/` were 1,157 passed and 2 skipped; the canary test
  puts a marker in the token, the cookie, the subject and the roles and finds
  it in no DEBUG log, span, body or header.
- **Y1b, the key-set client** (after the first security review's two high
  findings): the request asks for an uncompressed answer and a compressed one
  is a failed fetch (a 193 KB gzip answer of 190 MiB stays under a 2 MiB bound
  in the test); a fresh key is served without taking the fetch lock; a stale
  one is served up to 24 hours, with a warning; a failed fetch logs one warning
  naming the failure's class; a key is kept only if it is RSA of 2,048 to 8,192
  bits, usable to verify, one of at most 16. 107 tests in `test_signin_keys.py`

  the signature and the module every claim (the issuer, the audience exactly
  the client id, the authorised party, the type, the expiry with no leeway,
  the nonce in constant time); `signinflow.py` holds the settings, the code
  exchange at a back-channel address that is a setting and is never taken
  from the discovery document, under one deadline, and `SigninFlow` with
  `start`, `finish` and `sign_out`. A refusal is one of 32 reasons from a
  closed list, logged once per reason per minute without a token, a code, the
  verifier, the nonce or a cookie value; the caller learns only that sign-in
  failed. Tested against the discovery document of the realm as it ran on kind
  (KR1; the fixture is that file): 416 tests, seen red on a scaffold and by
  eleven mutations. No route calls it.

**D2, as the runs settled it (the record the design asked for).** The design
left open what `iss` a token carries when a pod asks Keycloak by its Service's
name. With `--hostname` set to the front URL and
`--hostname-backchannel-dynamic=true`:
- the issuer is always the front URL,
  `http://id.meridian.localhost:8088/realms/meridian-staff`: in the discovery
  document whichever name it is asked at, in a client-credentials token asked
  for at the Service's name, and in the access and ID tokens of a code
  exchanged at the Service's name (the rig, in a container, three runs that
  agreed; `keycloak-tokens.md`, section 3, in the step's handoff folder);
- only the back-channel addresses follow the name asked: the token and key
  URLs name the Service when the document is asked for at the Service, and
  the authorization and end-session addresses stay on the front name;
- on the kind cluster (KR1): the discovery document through the edge names
  the front address as its issuer and on every endpoint, and the same
  document fetched by the Service's name from the Claims API's pod names the
  front URL as its issuer.
So the app pins the issuer to the front URL in every environment and takes the
key and token URLs as back-channel settings (the Service's name on kind); a
setting that pins the Service's URL as the issuer refuses every token. Y3 is
built on that: its front-channel and back-channel addresses are separate
settings. **Not seen on the cluster:** a token (no script asks for one there
before Y7), so the token's `iss` is a container measurement, and the key URL
fetched from the Claims API's pod (Y4). The decision record (ADR) stays with
the contract that wires the first route, as designed (Y8).

**The two further security passes and what Y4 may do.**
- **Second security review** (of the fixes, 2026-10-07): `NOT YET`. It closed
  the first review's gzip bomb, both exception paths, the error on a plain-HTTP
  key URL through `from_env`, the subject, `via`, the cap at open, the silent
  fetch and the key bounds; it found 9 findings: **1 high** (a key URL that
  drips its response headers wedges the fetch lock for good, found with a
  real socket), **1 medium** (the refusal hook ran on every refusal, so a
  flood was a write per request) and **7 low** (a hook that raises a
  `BaseException` gives a 500; the session key's docstring over-claimed; the
  token type and authorised parties are empty by default; the subject has no
  character rule yet; the settings error; blind spots of the route walk; clock
  skew at the cap). The high and the medium were fixed by Y1c.
- **The re-check** (of Y1c, 2026-10-08): **`Y4 MAY WIRE IT`**. The high finding
  is closed on a real socket under the real deadline (each drip is cut at five
  seconds, the lock is free, the next due fetch succeeds) and the re-check
  found no critical or high finding. It found **1 medium** (the event-loop
  guard tripped only for a bearer token with a key id; closed by Y1d) and
  **5 low** (a name lookup that hangs holds the fetching caller for the
  resolver's time, and the module's sentence said "served at once"; the
  connect timeout must stay below the deadline, now pinned by a test; the
  certificate context built per fetch costs about 37 ms; two methods of the
  model library skip the settings' validators, and the docstring said none
  did; the last window of a flood is never given to the hook). Y1d closed the
  medium and three of the low; of the other two, the context's cost needs no
  change and the flood's last window is inherent to the design (rule 4).
- **What it allows, and under which rules.** Y4 may wire the guard into the
  Claims API's routes if it follows these. (1) `check_bearer` and the key
  fetch run only from a plain `def` dependency; a call on an event loop is a
  bug and a 500, not a 503. (2) The walk test runs on the production app
  factory with no dependency overrides, sends a valid RS256 bearer with a key
  id to every guarded form of route, asserts a role on every state-changing
  route and names mounts and websockets in its closed list; no websocket until
  a guard that works for one exists. (3) The settings come only from
  `from_env`, one `KeySet` per population, shared; `MERIDIAN_ENVIRONMENT` is
  set on the Claims API (otherwise a plain-HTTP edge stops the start on kind);
  the token type and the authorised parties are set from a live token before
  the switch is turned on. (4) The refusal hook is cheap or owns its retry: it
  takes the reason, the request and the carried count, is called once per
  reason per window, and a failed call is not repeated until the next window
  (the gateway's hook releases its window on a failure; the difference is
  deliberate), so the audit row must not promise exact totals. (5) A route
  that changes state and accepts the cookie checks the request's origin when
  `via` is `cookie`; no route returns a `Principal`; a refusal is caught as
  `SigninRefusal`, not as `Unauthenticated` alone. (6) The page flow catches
  the refusal from `set_session_cookie` and the `ValueError` from
  `seal_session`. (7) A subject, a role, a cookie or a token is never put in an
  exception's text or a log argument; the service middleware's streaming path
  (a span carries the exception's text once a response has started) is fixed
  before a route can raise with a subject in it. (8) Operations: pods get a
  short resolver timeout and few search dots, the previous session key is
  removed after eight hours, and a restart of the mock issuer that makes new
  keys gives up to 30 seconds of 401 to a bearer token.

**What a live token of the pinned Keycloak holds** (the opt-in rig, three runs
that agreed; no secret or token is written anywhere). The access tokens of both
clients are accepted with their roles; the settings must name:
- the issuer, `http://id.meridian.localhost:8088/realms/meridian-staff`, the
  front URL on every path (a token asked for at the Service's name still
  carries it; a setting that pins the Service's URL refuses every token);
- the audience, `meridian-claims-api`, a string and not a list, different from
  both client ids;
- the authorised party, `meridian-claims-web` for the pages and
  `meridian-scripts` for the scripts, and the token type `Bearer`;
- the subject, `sub`, 36 characters, the same after a new container (because
  the generator names the user ids);
- the roles, a top-level `roles` list, a list even for one role;
- **no `nbf`**: Keycloak sends none, so the module does not require it. The
  first draft of Y1 required it and a report named that line as the likeliest
  to break on a live token; the code no longer requires it (checked when
  present), and the live token confirms the choice.
The ID token carries the client id as its audience and is refused on it (its
`typ` is `ID`, so the type setting would refuse it too); the refresh token is
signed HS512 and refused on its algorithm. The image is 750,682,782 bytes
(about 716 MiB), runs as user 1000 and has no `curl`, `wget` or `nc`, so its
probes are HTTP ones; it was ready in about 13 seconds and held 600 to 700 MiB
of a 1 GiB limit without an out-of-memory kill. A new container makes new key
ids; a service with a cold key cache refuses a token from before it
(`unknown-key`), one with a warm cache accepts it for up to an hour, and the
cookie, which holds no token and is not checked against the issuer, lives on.
The access token also carries `email`, `name` and `preferred_username`
(synthetic here); the module reads none of them.
