### S099 — A dispatcher and workers: the test lock and the two briefs

**Status:** done · **Started:** 2026-10-08 · **Finished:** 2026-10-08
**Goal:** the plan's steps run in worker sessions, one step and one worktree
each, handed out by a dispatcher session, and what keeps two sessions apart on
one machine is a script and not a rule both have to remember.
**Decisions:**

- The owner, 2026-10-08, after three days of five steps side by side in one
  session had used 86 % of the weekly limit: "i want more session once with
  seperated worktree so i can optimalise the context long and we can work
  quicker ... somehow we should apply your policies where two worktree dont
  try the test in the same time"; to the session's proposal (a queue, locks in
  scripts, worker sessions, this session a thin dispatcher): "Okay, yes and you
  will be the orchestrator this way"; on a brief for the dispatcher: "if i open
  a new session and i want you as an orchestrator you can read it and you will
  be in context immediateli"; and on where the process lives: "this process we
  should implement in the repo and at development base too".
- **One exclusive lock, no tiers.** `make pytest`, `make pytest-db` and each
  container of `make alerts` take it; `make eval` and `make eval-baseline`
  reach it through `make pytest-db`. A test file run by hand takes none: one
  file is not what froze the machine. Rejected: a shared lock for runs without
  a database beside an exclusive one for runs with one (two modes to get
  wrong, for a wait of seconds).
- **Sourced by the recipe, not a wrapper around a second target.** The first
  design was `scripts/with_machine_lock.sh <label> <command>` with the old
  recipes moved under `pytest-db-run` and `alerts-run`. Read before building:
  four tests read the recipes under their public names
  (`tests/meridian/test_ci_config.py`, `test_alert_rules.py`,
  `test_cost_dashboard_gap.py`, `test_smoke_trap.py`), and a recipe line that
  holds `$(MAKE)` runs under `make -n`, so a dry run would have taken the real
  lock and a test inside the suite that dry-runs a target would have waited on
  the suite's own lock. So `scripts/machine_lock.sh` is sourced by the
  recipe's shell, which then holds the `flock` on descriptor 9 to its end: the
  recipes stay where they were, `make -n` prints the line and takes nothing,
  and the kernel frees the lock when the run's last process is gone.
- **In `pytest-db` the lock comes before the first removal and before the exit
  trap.** The recipe's first act is to remove the containers of its name and
  its trap removes them again; a run that gives up waiting must reach neither,
  or it ends the holder's database. A test pins the order.
- **No switch.** The first design let `GITHUB_ACTIONS=true` pass through. That
  variable is set by hand on the development machine before a push (so that
  the stand-in change-log name is refused), which would have made it the way
  round the lock. The lock is taken in CI too, where nothing else holds it;
  the one fallback is a machine without `flock`, which says so and runs.
  `MERIDIAN_LOCK_DIR` moves the lock and exists for its tests;
  `MERIDIAN_LOCK_WAIT=0` does not wait and is no way past a held lock.
- **It holds whether the cluster is up or not.** Two database runs that would
  have fitted side by side without the cluster now run one after the other.
  Accepted: the cluster is up on most days, and a rule with a condition is the
  kind two sessions get wrong.
- **The role is a skill, and the skill is the brief.** `plan-dispatcher` and
  `plan-worker` under `.claude/skills/`, mirrored to `.agents/skills/` so Codex
  reads them. No slash command files and no second copy under `docs/`. Their
  bodies name no project; the last section, "This repository", carries the
  plan's path, the two-worker limit and the targets, as `docs-sync` does with
  its table, so the development base's copies differ in that section only.
- **The board stays outside the repository** (a board in the tree would be
  edited by every branch), and so do the workers' status files. The skills
  say that the card or the session's memory gives the board's path; no path of
  the machine is in a tracked file.
- **The stop hook `check-lanes.sh` is left as it is.** It reads a board of
  sub-agent lanes inside one session. The dispatcher's board is another file
  on purpose: one board, not two.
- **Two workers at once**, one that holds the cluster and one that does not,
  chosen by the files their branches touch.

**Review:** the `code-reviewer` read the lock's commit (the script, the
Makefile's lines, the test) and ran its own experiments beside a lock folder
of its own. One must-fix and four to improve:

- **Must fix, done.** `make pytest` and the two containers of `make alerts`
  no longer stopped at a SIGTERM to make. The old recipe line was one command
  and make ran it itself; with `&&` in the line make starts a shell, the shell
  dies at the signal and the run lives on with the lock (what
  `timeout 600 make pytest` would leave behind). The recipes now say
  `$(MACHINE_LOCK) && exec ...`, so make's shell becomes the run. A test with
  a small Makefile of the same idiom sends the signal and takes the lock
  afterwards; without `exec` it fails. `make pytest-db` was a shell block
  before this step and is as it was.
- **Done.** Under bash a lock file that cannot be opened read as a lock that
  is held (dash leaves at the failed redirection). The script says "cannot
  open" and exits 73; tested under both shells.
- **Done.** The tests no longer inherit the caller's `MERIDIAN_LOCK_WAIT` or
  `MACHINE_LOCK_LABEL`.
- **Done.** Three cases that were missing: a recipe of `pytest-db`'s shape
  that gave up waiting reaches neither the removal nor the trap; a process
  the run left behind still holds the lock; the signal above.
- **Not taken.** Emptying the holder's record when the lock is taken, so that
  a holder that wrote none is not named as the last one. Every holder that
  comes through the script overwrites the record at once; only a process
  that took the file's lock some other way leaves the older line, and the
  tests' stand-in is the one that does.

It checked and found sound: the `exit` inside the sourced file under `set -e`
in both shells, a wait of 0 and of twenty digits, that the lock lasts to the
last process of the run after a SIGKILL of make, and that no target or test
in the suite waits on a lock of its own. It did not check `make -j`, another
`/bin/sh` than dash and bash, or a test that leaves a daemon behind.
