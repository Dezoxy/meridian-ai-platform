## Threat model

Status on 2026-10-04, version 1 (the end of milestone M1): mostly
implemented, on a laptop. Six services, among them three tool servers, the
adjuster's and the claimant's pages and a scheduled sweep run in tests and
on the local kind cluster, and the gateway has called Azure OpenAI from a
laptop. No Meridian service runs in Azure, and there is no sign-in, no TLS
and no service identity yet (milestone M2); since S019 network policies on
kind say which pod may call which. Of the 111 threats, 43 are
implemented, 53 implemented in part, 8 implemented on kind, 2 designed, 4
open and 1 accepted (T-93 to T-99, S037, T-100, S036, T-101, S068, T-102,
S079, T-103 to T-107, S020, and T-108 to T-111, S080, are the last nineteen;
the five of S020 are about a Terraform module for Azure that is written,
validated and never applied, so no row of them was seen to hold, and the
four of S080 are about an upload path that is implemented and tested and was
seen on kind once, with both switches on for one run). For this version every
row's status was compared with the plan's steps, and one or two claims of each
implemented row with the code (S018).

The labels extend C-07's implemented, simulated and designed:

- **Implemented**: the mitigation the row names is built and tested. What it
  leaves is the row's residual, with the step that ends it.
- **Implemented in part**: part of the named mitigation is built; the row
  says which part, and which step holds the rest.
- **Implemented on kind**: built and checked on the local cluster only.
- **Designed**: nothing is built; the row names the step that builds it.
- **Open**: the main mitigation is not decided; the row says what stands in
  until it is.
- **Accepted**: the risk is taken, not mitigated.

A control that is simulated (the replay provider, the hashed embedding) is
called so in its row. "No step yet" means that no step's "done when" in the
plan covers the control; the plan's follow-up backlog lists it.

This register owns the `T-NN` IDs. Data classes are defined in the
[data classification](data-classification.md); measurable targets are in the
[quality attributes](../requirements/quality-attributes.md). Before building
a security-relevant feature, run the `feature-threat-model` skill and add or
refresh rows here.

### Trust boundaries

Each boundary is a place where the caller and the callee trust different
things. The relationships named are the main ones of the architecture model
(`model/containers.dsl`), so a changed relationship shows which boundary to
revisit. The rest are covered by single threats: database writes by T-25,
telemetry exports by T-03, registry reads by T-35, and the gateway's rate
store by T-45 and T-92: the model holds the store inside the Model Gateway,
not as a container of its own, so no relationship names it (S066).

| Boundary | Between | Relationships in the model |
|---|---|---|
| TB-1 | People and the platform | Claimant and adjuster to Ingress over HTTPS; operator to the Observability Stack |
| TB-2 | Edge and the workload APIs | Ingress to the Claims Triage App; the app validates user tokens against Entra ID (designed, S021) |
| TB-3 | Workload plane and control plane | Claims Triage App to Agent Runtime with a service identity; Evaluation Harness to the Claims Triage App; the workload's graph package inside the runtime process |
| TB-4 | Callers and the Model Gateway | Agent Runtime to gateway with tenant and agent headers, over mutual TLS (S055); Knowledge MCP Server to gateway for embeddings |
| TB-5 | Model Gateway and the outside | Gateway to Azure OpenAI and Mistral (designed, S023); gateway to Key Vault for provider credentials (designed) |
| TB-6 | Agent Runtime and tools | Runtime to the Policy, Knowledge and Claims MCP servers; the servers to the Platform Database |
| TB-7 | Untrusted content and the model context | Claimant text, retrieved wording, tool results and model output entering a prompt or a decision |
| TB-8 | Agent proposal and human decision | A paused run, the adjuster's decision through the Claims Triage App, the resumed run and its audit record |
| TB-9 | Git and the running platform | Registry changes by pull request; dependencies, images, credentials and configuration reaching the cluster |

TB-3 is partly not a network boundary: the runtime hosts the workload's graph
package in its own process (ADR 2), so graph code runs with the runtime's
database and gateway credentials. TB-7 is not a network boundary at all: the
content crosses no socket a firewall could guard, which is why its
mitigations sit in the runtime and the workload.

### Assets

- Personal data of claimants: claims, contact details, free-text
  descriptions, and every prompt, completion and checkpoint that carries
  them.
- Provider credentials, signing secrets, the delivery pipeline's cloud
  identity and the Terraform state; and, if a self-managed cluster is ever
  applied, its own keys (the certificate authority's, the admin kubeconfig, a
  join token, etcd: T-102).
- Approval decisions and their audit trail: who decided what, on which
  proposal, when.
- The Platform Database's space, which the audit trail shares with any stored
  file (T-108), and the adjuster's browser, the only reader of a file (T-109).
- Budgets and quotas, which are money.
- The registry: which deployment may see which data class, which agent may
  call which tool.
- The golden set and the evaluation gate, which decide whether a prompt or a
  model change may ship.
