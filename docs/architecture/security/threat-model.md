## Threat model

Status on 2026-10-04, version 1 (the end of milestone M1): mostly
implemented, on a laptop. Six services, among them three tool servers, the
adjuster's and the claimant's pages and a scheduled sweep run in tests and
on the local kind cluster, and the gateway has called Azure OpenAI from a
laptop. No Meridian service runs in Azure, and there is no sign-in, no TLS
and no service identity yet (milestone M2); since S019 network policies on
kind say which pod may call which. Of the 87 threats, 40 are
implemented, 39 implemented in part, 4 implemented on kind, 2 designed, 1
open and 1 accepted. For this version every row's status was compared with
the plan's steps, and one or two claims of each implemented row with the
code (S018).

The labels extend C-07's implemented, simulated and designed:

- **Implemented**: the mitigation the row names is built and tested. What it
  leaves is the row's residual, with the step that ends it.
- **Implemented in part**: part of the named mitigation is built; the row
  says which part, and which step holds the rest.
- **Implemented on kind**: built and checked on the local cluster only.
- **Designed**: nothing is built; the row names the step that builds it.
- **Open**: the main mitigation is not decided; the row says what stands in
  until it is.
- **Accepted**: the risk is taken, not mitigated.

A control that is simulated (the replay provider, the hashed embedding) is
called so in its row. "No step yet" means that no step's "done when" in the
plan covers the control; the plan's follow-up backlog lists it.

This register owns the `T-NN` IDs. Data classes are defined in the
[data classification](data-classification.md); measurable targets are in the
[quality attributes](../requirements/quality-attributes.md). Before building
a security-relevant feature, run the `feature-threat-model` skill and add or
refresh rows here.

### Trust boundaries

Each boundary is a place where the caller and the callee trust different
things. The relationships named are the main ones of the architecture model
(`model/containers.dsl`), so a changed relationship shows which boundary to
revisit. The rest are covered by single threats: database writes by T-25,
telemetry exports by T-03, registry reads by T-35.

| Boundary | Between | Relationships in the model |
|---|---|---|
| TB-1 | People and the platform | Claimant and adjuster to Ingress over HTTPS; operator to the Observability Stack |
| TB-2 | Edge and the workload APIs | Ingress to the Claims Triage App; the app validates user tokens against Entra ID (designed, S021) |
| TB-3 | Workload plane and control plane | Claims Triage App to Agent Runtime with a service identity; Evaluation Harness to the Claims Triage App; the workload's graph package inside the runtime process |
| TB-4 | Callers and the Model Gateway | Agent Runtime to gateway with tenant and agent headers, over mutual TLS (S055); Knowledge MCP Server to gateway for embeddings |
| TB-5 | Model Gateway and the outside | Gateway to Azure OpenAI and Mistral (designed, S023); gateway to Key Vault for provider credentials (designed) |
| TB-6 | Agent Runtime and tools | Runtime to the Policy, Knowledge and Claims MCP servers; the servers to the Platform Database |
| TB-7 | Untrusted content and the model context | Claimant text, retrieved wording, tool results and model output entering a prompt or a decision |
| TB-8 | Agent proposal and human decision | A paused run, the adjuster's decision through the Claims Triage App, the resumed run and its audit record |
| TB-9 | Git and the running platform | Registry changes by pull request; dependencies, images, credentials and configuration reaching the cluster |

TB-3 is partly not a network boundary: the runtime hosts the workload's graph
package in its own process (ADR 2), so graph code runs with the runtime's
database and gateway credentials. TB-7 is not a network boundary at all: the
content crosses no socket a firewall could guard, which is why its
mitigations sit in the runtime and the workload.

### Assets

- Personal data of claimants: claims, contact details, free-text
  descriptions, and every prompt, completion and checkpoint that carries
  them.
- Provider credentials, signing secrets, the delivery pipeline's cloud
  identity and the Terraform state.
- Approval decisions and their audit trail: who decided what, on which
  proposal, when.
- Budgets and quotas, which are money.
- The registry: which deployment may see which data class, which agent may
  call which tool.
- The golden set and the evaluation gate, which decide whether a prompt or a
  model change may ship.

### Threat register

disclosure, D denial of service, E elevation of privilege. T-33 is a human
oversight risk that STRIDE has no letter for.

### Residual risk

- T-01 is open, and so are T-38's uploads. Claimant identity is a product
  decision (how a claimant proves who they are without a staff account) and
  waits for the identity step (S021); the claimant pages exist since S049.
  Until it is decided, a claim may
  name any policy number, and the policy tools serve that policy's cover
  and claim history to the claim's run (T-22). Document upload has no
  design yet.
- T-66 is implemented in part, and its residual is accepted by the owner
  (2026-10-03): the claimant's pages stamp the report date, and the JSON
  route keeps its caller's date until callers are identified (S021). The
  loss date stays the claimant's word, and T-76's history can be padded
  by claims planted on a policy until a claimant is tied to one; both
  end at an adjuster, not at a payment.
- T-09 is accepted: workload code shares the runtime's process and
  credentials, which holds only while every workload is this repository's
  own reviewed code.
- T-13, T-26 and T-27 depend on detection that is never complete. The
  mitigations cap the damage (allowlists, argument binding, deterministic
  routing, a person on every material decision) rather than promising
  detection.
  S032 measured the injection screen on its own cases: 24 of 66 attacks
  stopped, and 16 of 22 look-alike sentences flagged. The caps held in
  every case; the screen is a first line and not the defence.
- From S047 the triage graph's model call reads the claimant's description
  with the claimant's name and e-mail replaced and other identifiers
  redacted, and only when the description holds no special-category data
  and does not address the model. Each screen is a heuristic (T-73): a miss
  sends what it missed to an EU deployment under the class `personal`. The
  model's answer can change two things: whether a claim within the threshold
  is approved automatically, and the recommendation an adjuster reads
  (T-26; S032 counted both). Its rationale, at most 600 characters,
  is redacted before it is stored, and may still quote the description.
- Two posts of one claim at the same moment no longer each store a proposal
  (S009's race): since S015 a triage takes the claim's row lock and moves it
  to `triaging` before it starts a run, so the second post finds the claim
  taken, and a claim is triaged at most five times (T-38).
- T-33 is a process risk. The UI can make a careless approval harder; it
  cannot make it impossible.
- T-35: with one maintainer, nobody reviews a change but its author. The
  required checks carry the whole weight.
- Since S055 the runtime, the gateway and the tool servers know which
  service calls them, from its certificate (mutual TLS, ADR 4), and refuse
  a tenant or agent outside that service's entry in the registry (T-08,
  T-24, T-48). What remains: the identity is a service's and not a
  person's until sign-in exists (S021); a stolen key is good until its
  certificate expires, and nothing restricts who may ask the issuer for a
  certificate (T-88); the edge and its hop to the Claims API have no TLS
  (S020, T-90). The tool servers still bind a call to a running run and
  to that run's claim (T-50), and a search costs the run's tenant (S046,
  T-62).
- The Claims API accepts a caller's W3C trace context, so a caller can
  attach a request to a trace ID it chose. The samplers ignore the caller's
  sampled flag, so a request cannot hide from the traces (S041). Whether
  the Azure edge strips or regenerates trace context is decided in S020.
- Provider-side abuse monitoring may retain prompts for a limited time under
  the provider's terms. It is accepted for synthetic data and recorded for
  the provider onboarding checklist in S034.
